OpenAI Responses API

The Responses API uses event: + data: SSE format over HTTP, and is also available over WebSocket. aimock supports both transports with the same fixtures.

Endpoints

Method Path Format
POST /v1/responses HTTP SSE (event: + data:)
WS /v1/responses WebSocket JSON messages

Unit Test: HTTP SSE Text Response

responses-text.test.ts ts 
import { createServer, type ServerInstance } from "@copilotkit/aimock/server";

const instance = await createServer([
  { match: { userMessage: "hello" }, response: { content: "Hi there!" } }
]);

const res = await post(`${instance.url}/v1/responses`, {
  model: "gpt-4o",
  input: [{ role: "user", content: "hello" }],
});

// Parse event: + data: SSE format
const events = res.body.split("\n\n")
  .filter(b => b.includes("event: ") && b.includes("data: "))
  .map(b => ({
    type: b.match(/^event: (.+)$/m)[1],
    data: JSON.parse(b.match(/^data: (.+)$/m)[1]),
  }));

const types = events.map(e => e.type);
expect(types).toContain("response.created");
expect(types).toContain("response.output_text.delta");
expect(types).toContain("response.completed");

SSE Event Sequence

The Responses API uses typed events. A text response produces this sequence:

  1. response.created
  2. response.in_progress
  3. response.output_item.added
  4. response.content_part.added
  5. response.output_text.delta (one per chunk)
  6. response.output_text.done
  7. response.content_part.done
  8. response.output_item.done
  9. response.completed

Function call responses follow the same pattern but use response.function_call_arguments.delta and response.function_call_arguments.done events. Custom tool calls use response.custom_tool_call_input.delta and response.custom_tool_call_input.done — see Namespaced and custom tool calls.

The same fixtures work for both HTTP SSE and WebSocket transports. See the WebSocket APIs page for WebSocket-specific details.

Ordered blocks (tool-first)

A combined content + toolCalls fixture accepts an optional blocks array to control stream order — see Ordered blocks. The Responses API has full support: output items (message, function_call or custom_tool_call) are assigned output_index in array order, so a tool call can precede the message and SDKs honor the ordering.

Namespaced and custom tool calls

The Responses API has two more tool-call shapes. aimock emits both over HTTP (streaming and non-streaming) and over WebSocket:

  • A function_call with namespace. A tool offered inside a {"type": "namespace", "name": "...", "tools": [...]} tool is called with its namespace next to its name. Codex puts each MCP server's tools in one namespace and sub-agent tools in the collaboration namespace.
  • A custom_tool_call. A custom (freeform) tool ({"type": "custom", ...}, with an optional Lark or regex grammar) is called with free-text input, not JSON arguments. Codex's apply_patch is a custom tool.
fixtures/codex.json json 
{
  "fixtures": [
    {
      "match": {
        "userMessage": "Look up aimock",
        "toolName": "search",
        "toolNamespace": "mcp__docs",
        "hasToolResult": false
      },
      "response": {
        "toolCalls": [
          { "name": "search", "namespace": "mcp__docs", "arguments": { "q": "aimock" } }
        ]
      }
    },
    {
      "match": { "userMessage": "add hello.txt", "hasToolResult": false },
      "response": {
        "toolCalls": [
          {
            "type": "custom",
            "name": "apply_patch",
            "input": "*** Begin Patch\n*** Add File: hello.txt\n+hello\n*** End Patch\n"
          }
        ]
      }
    },
    {
      "match": { "hasToolResult": true },
      "response": { "content": "done" }
    }
  ]
}

mcp__docs is the namespace Codex gives an MCP server named docs. Each tool-call fixture is gated with hasToolResult: false and the last fixture answers every follow-up, so each call is made once and the agent stops. See the Codex recipe below.

A toolCalls entry without type (or with "type": "function") is a function call, as before. An entry with "type": "custom" is a custom tool call: it takes input, which aimock never parses or stringifies, and it may also carry namespace. Both kinds mix in one toolCalls array and keep its order. In ordered blocks, a toolCall block takes namespace, and a customToolCall block is a custom tool call.

"customToolCall" is a blocks type only. A toolCalls entry with "type": "customToolCall" is an error: fixture validation (aimock validate, --validate-on-load, addFixturesFromJSON(), POST /__aimock/fixtures) rejects it, and a fixture that is not validated (a file loaded by loadFixtureFile() or loadFixtureDir(), a programmatic or a factory fixture) fails each request with aimock_invalid_fixture_tool_call. Releases up to 1.44.0 served such an entry as a function call. Use "type": "custom" for a custom call in toolCalls.

Event sequences

A namespaced function call streams exactly like any function call. The only change is namespace on the function_call item in response.output_item.added, response.output_item.done and response.completed. A call without a namespace has no namespace key, so existing fixtures produce the same output as before.

A custom tool call at output_index k streams as:

  1. response.output_item.added: a custom_tool_call item with id ctc_…, call_id, name, optional namespace, input: "" and status: "in_progress"
  2. response.custom_tool_call_input.delta, one per chunk (none when input is empty)
  3. response.custom_tool_call_input.done with the full input
  4. response.output_item.done: the same item with the full input and status: "completed"

A non-streaming response has the completed item in output. The call_id is the fixture's id when set.

Only the Responses API can serve a custom tool call. Every other provider endpoint (Chat Completions, Anthropic Messages, Gemini, Gemini Interactions, Bedrock, Ollama, Cohere, Realtime, Gemini Live) rejects it before any content, with the code aimock_unsupported_tool_call. Ollama /api/generate is the exception: it rejects every tool-call fixture with HTTP 400 (invalid_request_error) and no aimock code. This applies to a custom toolCalls entry and to a customToolCall block. The message names the tool and the API, for example aimock: fixture tool call "apply_patch" is a custom tool call, which only the OpenAI Responses API supports; this request arrived on OpenAI Chat Completions. The fixture itself loads without error; the rejection happens per request. Fixture validation (aimock validate, --validate-on-load) warns about a file fixture with a custom call that sets an endpoint other than "chat", because such a fixture can never serve it. Those endpoints ignore namespace on a function call and send the bare tool name.

A malformed tool call in a programmatic fixture (addFixture, on), in a response factory's result, or in a file fixture loaded without validation is also rejected per request, because those fixtures are not load-validated. This applies to toolCalls entries and to tool-call blocks. Examples: a custom call whose input is not a string, an empty namespace, a toolCalls entry with "type": "customToolCall", or a toolCall block that carries input. The request fails before any content with the code aimock_invalid_fixture_tool_call and a message such as Invalid fixture tool call: "input" must be a string for a custom tool call (toolCalls[0]). The journal entry records the message. A function call in toolCalls with any other type (including the legacy "toolCall") or with an input field is still served as a function call, as in earlier releases; file validation only warns about it. The exception, on the OpenAI Responses API only, is an entry whose type is unknown (not "function", "custom" or "toolCall", for example a mistyped "custom_tool_call") and whose arguments is not a string: it gets aimock_invalid_fixture_tool_call.

One malformed case does not get this code. A function call in toolCalls with no type, "function" or "toolCall" whose arguments is not a string (omitted, null, a number or a boolean, or an object or array in a fixture passed to addFixture, addFixtures, prependFixture or createServer; on, a response factory's result and file loading convert an object or array to a string) still fails as in earlier releases: HTTP 500 with no code, the message Invalid fixture tool call: "arguments" must be a string after normalization, and no error in the journal entry. This applies to file fixtures too. An arguments string that is not valid JSON is sent unchanged.

The order of the checks: toolCalls entries are checked in array order, and the first failure wins. In each entry, an entry that is not an object or that has "type": "customToolCall" is rejected first, with aimock_invalid_fixture_tool_call, on every endpoint. Then, on an endpoint other than the Responses API, a custom call is reported as aimock_unsupported_tool_call before its fields are checked, so a custom call with a bad name, input, arguments, id or namespace still gets that code.

Both codes are carried in the provider's error shape:

  • OpenAI Responses, OpenAI Chat Completions, Azure OpenAI and Cohere: HTTP 500 with error.code in an OpenAI-style envelope. Cohere gets this envelope, not its native error shape.
  • OpenRouter Chat Completions: HTTP 500 with the code in error.metadata.reason. Its error.code is the numeric HTTP status.
  • Anthropic Messages: HTTP 500 in Anthropic's error envelope (error.type api_error), with the code in error.code.
  • Gemini Interactions: HTTP 500 with the code in error.code.
  • Gemini and Vertex AI: HTTP 500 with a google.rpc.ErrorInfo entry in error.details: reason is the code in upper case (for example AIMOCK_INVALID_FIXTURE_TOOL_CALL) and metadata.code is the code.
  • Bedrock: HTTP 500 with the code in reason, next to __type.
  • Ollama /api/chat: HTTP 500 with a code member next to the string error.
  • OpenAI Responses over WebSocket: an error event with the code in error.code.
  • Realtime: no error event. aimock sends response.created and then response.done with status: "failed" and the code in response.status_details.error.code.
  • Gemini Live: an error frame with code 13 and the same google.rpc.ErrorInfo detail as Gemini.

Matching

aimock flattens the request's tools before matching. Tools inside a namespace tool, custom tools, and the tools of an additional_tools input item (which Codex's responses-lite models send in place of tools), and the tools of a tool_search_output input item (tools loaded by tool search) are all visible. A malformed tool collection is rejected with HTTP 400 (invalid_request_error), or an error event over WebSocket: a tools value that is not an array (at the top level only, a falsy value such as false or "", or an object whose length is 0, counts as no tools), a null tool entry, or a namespace tool with an empty or missing name (its inner tools would otherwise lose their namespace; OpenAI's published spec also requires the name, with minLength: 1, in the NamespaceToolParam schema of openai/openai-openapi openapi.yaml version 2.3.0). A null entry is also rejected inside a namespace tool and in those input items, and so is a namespace tool with an empty or missing name in those input items. The falsy exception does not apply there: a namespace tool's tools must be an array, and an input item can omit tools, but any other value that is not an array is rejected. Matching then works as follows:

  • toolName matches any offered function or custom tool by name, whatever its namespace. Other tool types (web_search, file_search, mcp, and so on) are not visible to matching.
  • toolNamespace matches an offered tool's namespace exactly. Alone, it matches when any tool sits in that namespace. With toolName, one tool must carry both. There is no default namespace: a top-level tool has none. It matches any request tool that carries a namespace field. On this API, aimock sets that field on each tool inside a namespace tool. Chat Completions passes request tools through unchanged, so a top-level namespace field that a client sends there also matches. Anthropic Messages does not carry the field.
  • A predicate sees namespace on each tool in req.tools and on history tool calls.

History items custom_tool_call and custom_tool_call_output count as a tool round, so hasToolResult, toolCallId, toolResultContains and turnIndex work after a custom tool call. A content-array custom_tool_call_output is matched on its input_text parts.

Codex recipe

Gate the turn-0 fixture with hasToolResult: false and the follow-up with hasToolResult: true. Codex sends the same user prompt and the same tools on the follow-up, so without the turn-0 gate the turn-0 fixture matches again and the agent loops. A fixture that matches only on toolName or toolNamespace has the same problem: the tool is offered on every request, so that fixture matches every request before any later fixture gets a chance.

Codex configuration notes:

  • Point a custom provider at aimock (base_url = "http://127.0.0.1:4010/v1", wire_api = "responses") and use model gpt-5.5. Codex's other bundled models send their tools in additional_tools and run in code mode, and an unknown model slug gets no apply_patch tool.
  • Codex defers MCP tools behind tool_search, which aimock does not mock. Set omit_tools_from = ["deferred"] on the MCP server so its tools are offered directly, in a namespace named mcp__<server> (for example mcp__docs for [mcp_servers.docs], with no trailing __). toolNamespace is an exact match, so if a match fails, read the exact values from the aimock journal: each entry's body.tools[] carries namespace and function.name. With codex exec (approval policy never), also set default_tools_approval_mode = "approve" on that server, or Codex refuses the MCP call.
